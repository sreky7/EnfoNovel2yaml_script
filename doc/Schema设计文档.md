
# 剧本YAML Schema设计文档

## 一、设计背景与目标

### 1.1 需求背景
本Schema服务于小说转剧本自动化工具，核心目标是将3个章节以上的小说文字自动转换为结构化剧本格式，使作者可以快速获得可编辑、可进一步打磨的剧本初稿。

### 1.2 设计目标
| 目标 | 说明 |
|-----|------|
| **结构清晰** | 层次分明，便于人工编辑和程序解析 |
| **信息完整** | 包含剧本创作所需的全部核心要素 |
| **兼容性强** | 支持多场景、多角色的复杂剧情 |
| **扩展性好** | 预留扩展字段，支持未来功能迭代 |
| **语义明确** | 字段命名直观，降低理解成本 |

---

## 二、Schema整体结构

### 2.1 顶层结构

```yaml
drama_info:      # 剧本元信息（必选）
role_list:       # 全局角色库（必选，可空数组）
scenes:          # 场景列表（必选，至少1个场景）
```

### 2.2 核心设计原则

| 原则 | 设计考量 |
|-----|---------|
| **角色全局化** | 避免同角色多ID问题，确保角色贯穿全剧本一致性 |
| **场景独立化** | 每个场景自包含，便于单独编辑和调整顺序 |
| **内容结构化** | 旁白/动作/台词三分法，符合剧本创作惯例 |
| **元数据完备** | 记录来源、字数、时间等关键信息，便于版本管理 |

---

## 三、字段详细定义

### 3.1 drama_info（剧本元信息）

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| book_name | string | 是 | 剧本名称（取自小说文件名） |
| source | string | 是 | 素材来源标识 |
| total_scene | integer | 是 | 场景总数 |
| original_word_count | integer | 是 | 原始小说字数（不含空格换行） |
| create_time | string | 是 | 生成时间（格式：YYYY-MM-DD HH:MM:SS） |

**设计原因**：
- `book_name`：作为剧本的唯一标识，便于文件管理和版本追踪
- `source`：支持多来源扩展（本地txt、网络爬虫、数据库等）
- `total_scene`：快速了解剧本规模
- `original_word_count`：评估转换效率和内容完整性
- `create_time`：版本管理和审计追溯

### 3.2 role_list（全局角色库）

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| role_id | integer | 是 | 角色唯一标识（全局递增） |
| role_name | string | 是 | 角色名称（如：主角、袭老板） |
| role_desc | string | 否 | 角色简短描述（身份、性格、特征） |

**设计原因**：
- **全局去重**：避免同一角色在不同场景使用不同ID，确保跨场景角色一致性
- **role_desc**：辅助编剧理解角色设定，便于后续角色塑造

### 3.3 scenes（场景列表）

每个场景包含以下字段：

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| scene_id | integer | 是 | 场景序号（按章节顺序递增） |
| scene_title | string | 是 | 场景标题（取自章节名或自动生成） |
| location | string | 是 | 场景发生地点 |
| scene_synopsis | string | 是 | 场景剧情梗概（≤50字） |
| contents | array | 是 | 场景内容片段列表 |

**设计原因**：
- `scene_id`：场景唯一标识，支持场景重排序和引用
- `scene_title`：快速定位场景内容
- `location`：明确空间背景，符合剧本格式规范
- `scene_synopsis`：提供场景概览，便于快速浏览和剧情梳理

### 3.4 contents（内容片段）

内容片段支持三种类型：

| 类型(type) | 说明 | 必需字段 |
|-----------|------|---------|
| narrate | 旁白（环境描写、心理活动、场景转换） | type, content |
| action | 动作描写（角色行为） | type, role_id, content |
| dialogue | 对话台词 | type, role_id, content |

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|-----|------|
| type | string | 是 | 内容类型：narrate/action/dialogue |
| role_id | integer | 否 | 角色ID（仅action和dialogue必填） |
| content | string | 是 | 内容文本 |

**设计原因**：

#### 三分法设计原理

```
┌─────────────────────────────────────────────────────────────┐
│                    剧本内容层次模型                          │
├─────────────────────────────────────────────────────────────┤
│  narrate（旁白）                                            │
│  ├─ 功能：交代背景、环境、时间、心理活动                       │
│  ├─ 特点：无角色绑定，客观视角                                │
│  └─ 场景：段落开头、场景转换、心理描写                         │
├─────────────────────────────────────────────────────────────┤
│  action（动作）                                             │
│  ├─ 功能：描述角色的肢体动作、表情变化                         │
│  ├─ 特点：必须绑定角色，动态展现                              │
│  └─ 场景：对话间隙、情节推进、情绪表达                         │
├─────────────────────────────────────────────────────────────┤
│  dialogue（对话）                                           │
│  ├─ 功能：角色之间的语言交流                                  │
│  ├─ 特点：必须绑定角色，推动剧情                              │
│  └─ 场景：角色互动、冲突发展、信息传递                         │
└─────────────────────────────────────────────────────────────┘
```

**设计考量**：
1. **符合剧本创作规范**：旁白-动作-台词是剧本的经典三分结构
2. **AI解析友好**：明确的类型划分便于机器学习模型理解和转换
3. **编辑效率提升**：结构化内容便于选择性编辑和格式调整
4. **100%内容保留**：确保原文无丢字漏段，转换过程可逆

## 五、完整示例

```yaml
drama_info:
  book_name: 十霂街奇谭
  source: 本地txt小说素材
  total_scene: 3
  original_word_count: 15680
  create_time: '2026-06-07 15:30:00'

role_list:
- role_id: 1
  role_name: 主角
  role_desc: 高中生，好奇心强，意外闯入神秘古董店
- role_id: 2
  role_name: 袭老板
  role_desc: 古董店老板，一身白衣戏妆，神秘莫测

scenes:
- scene_id: 1
  scene_title: 神秘古董店
  location: 十霂街
  scene_synopsis: 主角清晨偶遇神秘古董店，推门而入遇袭老板
  contents:
  - type: narrate
    content: 清晨的十霂街空无一人，古铃随风轻响
  - type: action
    role_id: 1
    content: 缓步走过石板路，目光被一家独特的店铺吸引
  - type: dialogue
    role_id: 2
    content: 你...是怎么进来的？
```

## 六、约束规则

### 6.1 强制规则
1. **type约束**：仅支持 `narrate`、`action`、`dialogue` 三种类型
2. **role_id约束**：`narrate` 禁止出现 `role_id`，`action`/`dialogue` 必须绑定有效的 `role_id`
3. **内容完整性**：原文100%拆分，不得丢字漏段
4. **角色一致性**：同一角色名在全剧本中使用统一的 `role_id`

### 6.2 推荐规范
1. **scene_synopsis**：控制在50字以内，简明扼要
2. **role_desc**：包含身份、性格、关键特征，便于角色理解
3. **location**：具体明确，便于舞台调度
4. **内容分段**：按语义自然分段，每段不宜过长

## 七、扩展规划

### 7.1 预留扩展字段
| 字段位置 | 扩展字段 | 用途 |
|---------|---------|------|
| drama_info | author | 原著作者 |
| drama_info | version | 剧本版本号 |
| role_list | role_type | 角色类型（主角/配角/龙套） |
| scenes | scene_time | 场景时间（晨/午/晚/夜） |
| scenes | mood | 场景氛围（紧张/温馨/悬疑） |
| contents | emotion | 角色情绪（愤怒/悲伤/喜悦） |
| contents | duration | 表演时长预估 |

### 7.2 未来功能方向
1. **剧本格式导出**：支持转换为标准剧本格式（如Final Draft）
2. **角色关系图**：基于角色互动自动生成关系网络
3. **场景调度表**：根据location和time生成拍摄计划
4. **台词统计**：按角色统计台词数量，辅助戏份均衡

---

## 八、总结

本Schema设计遵循**结构化、完整性、易用性**三大原则：

1. **结构化**：通过分层设计（剧本→场景→内容片段）实现清晰的组织架构
2. **完整性**：覆盖剧本创作的全部核心要素，确保转换质量
3. **易用性**：字段命名直观，结构符合剧本创作习惯，便于人工编辑

该Schema经过V2.1版本迭代已正式定型，能够满足小说转剧本的核心需求，并为未来功能扩展预留了充足空间。

# DeepSeek全自动小说转剧本部署指南
## 步骤1：DeepSeek平台注册拿密钥
1.打开 https://platform.deepseek.com 注册账号；
2.左侧API Keys→Create new API Key，复制sk开头密钥填入config.ini。
## 步骤2：项目目录结构
NovelToScript
├─ source  存放待转换txt小说
├─ output  自动生成成品剧本
├─ doc     Schema规范文档
├─ config.ini 配置API密钥
├─ novel2drama.py
└─ requirements.txt
## 步骤3：安装依赖
pip install -r requirements.txt
## 步骤4：运行
python novel2drama.py
output自动生成成品yaml剧本，全自动拆分旁白/动作/台词，无需手动修改。

401：密钥错误；超时：网络重试；返回非json：不要修改Prompt。
